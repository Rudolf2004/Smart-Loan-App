Technical Project Report

Machine Learning and Multilingual LLM Support for the Smart Loan Application

Problem statement, model description, evaluation, interpretation, conclusion, limitations, and recommendations

Project: Smart Loan AppReport date: 22 July 2026Model family: Decision Tree ClassifierAI assistant: OpenAI Responses API

1. Introduction to the Problem Statement

Access to responsible credit is difficult when application procedures are complex, documentation requirements are unclear, and customers have different literacy, language, or accessibility needs. Manual assessment can also be slow and inconsistent. The Smart Loan App addresses these problems through a mobile-oriented digital application process supported by an explainable machine-learning estimator and a multilingual educational assistant.

The central problem is to help applicants submit complete, understandable loan applications while giving trained staff a consistent, auditable indication of how an application resembles previously learned lending patterns. The system must not replace lawful underwriting, discriminate against protected groups, or permit a general-purpose language model to make final approval or rejection decisions.

Project objectives

  • Collect and validate personal, employment, financial, loan, collateral, and guarantor information.
  • Transform application data into a consistent feature vector for machine-learning inference.
  • Return an advisory classification with class probabilities and confidence.
  • Explain forms, documents, and loan concepts in English, Twi, French, or Hausa.
  • Support people with disabilities through keyboard navigation, screen-reader labels, speech input, read-aloud output, large text, and high contrast.
  • Keep regulated lending decisions reviewable and under human control.

2. Description of the Models Used

2.1 Decision Tree loan-estimation model

The primary predictive model is a scikit-learn DecisionTreeClassifier exported into a versioned JSON bundle. The TypeScript backend validates the bundle and reproduces tree traversal during inference. At every internal node, a transformed feature is compared with a threshold; the application follows the left or right branch until reaching a leaf. Class counts stored at that leaf are normalized into percentages, and the class with the highest percentage becomes the advisory prediction.

The supported outcome classes are designed around APPROVED, CONDITIONALLY_APPROVED, and REJECTED. The interface deliberately describes them as predictions rather than final decisions.

Three important engineered ratios are calculated: debt-to-income ratio, loan-to-income ratio, and collateral-coverage ratio. Missing numerical values use stored imputation statistics; categorical values use stored fallback categories and one-hot encoding. The backend checks that the final vector has exactly the number of features expected by the trained bundle.

2.3 Multilingual large language model

The application also contains an OpenAI Responses API integration for an educational “Smart Loan Guide.” This model is not part of the predictive decision tree and cannot change the eligibility result. It explains processes, forms, documents, and general lending concepts in the selected language. The deployment model is configurable using OPENAI_MODEL; the current example configuration uses gpt-5.6-terra.

System instructions prohibit the assistant from approving, denying, or ranking applicants; requesting passwords, PINs, full identification numbers, or banking credentials; using protected characteristics; or promising rates and outcomes. Requests require authentication, have content-length and conversation limits, are rate-limited, and are sent with API storage disabled.

Important distinction: the decision tree produces an advisory pattern classification. The LLM provides language and educational assistance. A trained human reviewer remains responsible for the final lending decision.

3.2 Model-performance interpretation

No defensible predictive accuracy can currently be reported. The repository does not contain the exported loan_model_bundle.json, held-out predictions, confusion matrix, precision, recall, F1 score, ROC-AUC, calibration analysis, or subgroup fairness results. Software tests are not a substitute for evaluation on unseen lending data.

When a trained bundle is supplied, its leaf confidence represents the proportion of training class mass at the reached leaf. This should not automatically be interpreted as a calibrated probability that a borrower will repay. A high leaf percentage can still be unreliable when the leaf contains few records, the deployment population differs from the training population, or the data contains historical bias.

A proper evaluation should use an untouched test set and report per-class precision, recall, F1 score, confusion matrix, balanced accuracy, and probability calibration. Because false approvals and false rejections have different financial and social consequences, both error directions must be examined separately. Results should also be compared across relevant, legally reviewed subgroups to identify unfair performance differences without feeding protected characteristics into automated decisions.

4. Conclusion

The Smart Loan App demonstrates a sound separation of responsibilities. Structured machine learning provides a transparent, reproducible estimate; the LLM improves comprehension and multilingual access; accessibility controls reduce interaction barriers; and human review remains the final authority. The current implementation has a validated software foundation, but it is not yet sufficient evidence for production lending decisions because empirical model-quality and fairness results are absent.

The most valuable outcome of the architecture is not automation alone, but accountable assistance: users receive clearer guidance, staff receive a consistent advisory signal, and the application retains explicit boundaries around sensitive and regulated decisions.

5. Limitations

  1. Missing trained artifact: the required exported decision-tree bundle is not present in the repository.
  2. No dataset documentation: sample source, collection period, population, label definition, consent, missingness, and representativeness are unknown.
  3. No predictive metrics: accuracy and class-specific error rates cannot be verified from the available files.
  4. No fairness audit: disparate impact, equal-opportunity differences, and performance across relevant populations have not been measured.
  5. Decision-tree instability: a single tree can overfit and can change substantially with small changes in training data.
  6. Confidence may be uncalibrated: leaf class proportions are not guaranteed to be reliable real-world probabilities.
  7. LLM fallibility: the assistant can provide inaccurate or incomplete explanations despite its safeguards.
  8. Language coverage: interface-wide translation is not yet complete, and speech quality depends on browser support and available voices.
  9. Accessibility validation: automated features are present, but formal WCAG testing with users who have disabilities has not yet been completed.
  10. Regulatory dependency: deployment requirements vary by jurisdiction and require specialist legal, privacy, and compliance review.

6. Recommendations

  1. Document the dataset and outcome label, establish lawful use, remove leakage, and create reproducible train/validation/test splits.
  2. Export the trained model with training metadata and a model card containing intended use, excluded uses, version, owner, and review date.
  3. Report confusion matrices and per-class precision, recall, F1, balanced accuracy, calibration, and decision thresholds on an untouched test set.
  4. Conduct legally reviewed fairness testing and investigate disparities before deployment. Disability and other protected traits must not reduce access or influence automated outcomes.
  5. Compare the single decision tree with interpretable logistic regression and constrained ensemble alternatives. Choose using quality, stability, explainability, and fairness—not accuracy alone.
  6. Add applicant-facing reason codes based on validated decision paths, with an appeal and correction process overseen by staff.
  7. Monitor data drift, model drift, overrides, complaints, and subgroup performance; define rollback triggers and periodic revalidation.
  8. Complete professional translation and community review for English, Twi, French, and Hausa across the full interface.
  9. Run WCAG 2.2 AA audits and usability sessions involving screen-reader users and people with visual, hearing, motor, and cognitive disabilities.
  10. Evaluate the LLM using a multilingual question set covering accuracy, harmful advice, prompt injection, privacy leakage, refusal behavior, and human-escalation quality.
  11. Keep API keys server-side, minimize retained personal data, encrypt sensitive information, maintain access logs, and perform threat modelling.
  12. Do not move to automated approval or denial without validated evidence, documented governance, human oversight, and jurisdiction-specific legal approval.
Recommended deployment position: use the present system as an educational and decision-support prototype. Promote it to a production lending workflow only after the missing data, performance, fairness, accessibility, security, and compliance evidence has been completed and independently reviewed.
